# Retrieval-Augmented Legal Summarisation Plan

## 1. Research objective

Test whether cross-document retrieval improves an existing hierarchical legal
summarisation method, and whether verified legal citations identify more useful
evidence than semantic similarity alone.

The summarisation method is held fixed. Retrieval is the controlled independent
variable.

## 2. Baseline that remains unchanged

For every target document:

1. segment it into structured passages;
2. embed all passages and compute their mean document centroid;
3. rank passages by similarity to that centroid;
4. divide the document by original position into four contiguous groups;
5. pack the highest-ranked passages from each group into the Stage-1 budget;
6. generate one group brief; and
7. combine the four briefs into the final summary.

The experiment will replace the original Llama generator with the three fixed
encoder-decoder families, but it will preserve the algorithmic structure:

- T5-large
- BART-large-CNN
- PEGASUS-XSum

## 3. Proposed architecture

### 3.1 Offline index construction

```text
ReguSum index/train split only
        -> normalise source documents
        -> segment into retrieval chunks
        -> embed each chunk
        -> store vector + text + document/section metadata
        -> freeze and hash index
```

The index must never contain a held-out evaluation document or a gold summary.

### 3.2 Source-query inference

```text
held-out document
        -> unchanged four-group selection
        -> selected focal passages for group g
        -> derive query representation
        -> retrieve Top-K external chunks
        -> deduplicate and pack under evidence budget
        -> unchanged Stage-1 group brief
        -> unchanged Stage-2 document summary
```

The first implementation should query per group rather than once per complete
document. This aligns retrieved evidence with the existing Stage-1 unit and
limits broad, repetitive retrieval.

### 3.3 Summary-query inference

```text
selected focal passages for group g
        -> draft group brief using the unchanged summariser
        -> embed generated draft brief
        -> retrieve Top-K external chunks
        -> focal passages + retrieved evidence
        -> regenerated group brief
        -> unchanged Stage-2 document summary
```

The draft brief is generated by the model. The gold summary is prohibited as a
query.

### 3.4 Citation-guided and hybrid retrieval

Citation-guided retrieval uses explicit references in a group's focal passages
to retrieve verified legal targets. Hybrid retrieval combines this deterministic
signal with semantic retrieval:

```text
group focal passages
       |-- semantic Top-M candidates
       |-- verified cited targets
       -> union
       -> deduplicate
       -> rank under fixed evidence budget
       -> Stage-1 group brief
```

The graph is used for evidence selection, not for changing the four-group
summarisation structure.

## 4. Experimental conditions

### Required initial conditions

1. `base`: existing summariser, no external retrieval.
2. `rag_source`: group focal passages query the semantic index.
3. `rag_summary`: a generated draft group brief queries the semantic index.

### Conditions added after feasibility gates

4. `citation_rag`: retrieve verified cited targets.
5. `hybrid_rag`: combine semantic and citation evidence.
6. `shuffled`: provide length- and count-matched incorrectly aligned evidence.

The first pilot should not run every combination. Establish baseline
reproducibility and retrieval relevance before expanding the matrix.

## 5. Evidence packing and token fairness

For model `m`, define a fixed Stage-1 input ceiling `B_m` using that model's own
tokenizer and the published configuration. Within model `m`, every condition
uses the same `B_m`.

The existing group selection remains unchanged. Retrieved chunks enter a
bounded evidence allocation and displace content only according to one frozen
packing rule. The audit must record:

- focal tokens proposed and admitted;
- evidence tokens proposed and admitted;
- evidence rejected for duplication, irrelevance, or lack of space;
- final prompt token count;
- truncated passages; and
- model/tokenizer revision.

If the three models support different input lengths, comparisons of retrieval
effects are paired within each model. Cross-model differences must not be
described as retrieval effects.

## 6. Split and leakage policy

1. Obtain the exact ReguSum split used by the published study where possible.
2. Freeze document IDs in a versioned split manifest.
3. Build the index from the index/train side only.
4. Fine-tune models using the training side only.
5. Use development documents for Top-K and query-policy decisions.
6. Open the final test results only after configuration is frozen.
7. Assert in code that no test document ID occurs in the vector index.
8. Assert that no gold-summary text or embedding is stored in the index or used
   as a query.

## 7. Retrieval implementation specification

### Chunk records

Each indexed chunk should contain:

- stable chunk ID;
- source document ID;
- agency;
- section/path metadata;
- chunk text;
- token count for each generator tokenizer;
- embedding model and revision;
- source content hash; and
- citation identifiers where available.

### Query records

Each query should contain:

- evaluation document ID;
- group ID;
- condition;
- exact query text or pooled passage IDs;
- query hash;
- embedding revision;
- Top-K;
- retrieved chunk IDs and scores; and
- filtering/deduplication decisions.

### Retrieval policies to compare

- Per-passage search followed by reciprocal-rank or max-score aggregation.
- One pooled group embedding.
- One generated draft-brief embedding.

Select one source-query policy on development data and freeze it before test.

## 8. Feasibility gates

Do not launch full generation until all gates pass.

### G1 - Baseline reproducibility

- All three generators complete deterministic smoke tests.
- The unchanged baseline reproduces its own cached output exactly when resumed.
- Token manifests prove condition-independent baseline construction.

### G2 - Split isolation

- Zero evaluation IDs in the index.
- Zero gold summaries in indexed or query material.
- Dataset and split hashes recorded.

### G3 - Retrieval audit

- Manually inspect a stratified sample of source-query and summary-query
  retrievals.
- Record relevant, redundant, misleading, and unrelated results.
- Do not proceed if retrieved evidence is predominantly unrelated or duplicates
  the target passage without adding information.

### G4 - Budget parity

- Maximum and observed prompt lengths are matched within every paired
  comparison.
- No condition silently gains additional context capacity.

### G5 - Citation feasibility

- Citation edges used for retrieval pass a stratified precision audit.
- The target text is available for a sufficient number of evaluation documents.
- Citation evidence is demonstrably related to information that could enter a
  summary.

## 9. Evaluation

### Published metrics

- ROUGE-1 F1
- ROUGE-2 F1
- ROUGE-L F1
- BERTScore F1

### Retrieval and legal-quality diagnostics

- evidence relevance;
- evidence redundancy;
- citation target precision;
- factual consistency/faithfulness;
- legal-information coverage;
- contradiction rate;
- document-level wins, ties, and losses; and
- paired bootstrap confidence intervals.

Report full-population results and the citation/retrieval-eligible subset. The
eligible-subset definition must be frozen before examining condition outcomes.

## 10. Implementation sequence

### WP0 - Freeze the design

- Confirm exact split, model adaptation states, and query granularity.
- Recover published ReguSum embedding, index, Top-K, and decoding settings.
- Freeze the baseline prompt and token policy.

### WP1 - Create the new package and tests

- Add the importable package under
  `phase 3 RAG summariser/src/summariser_rag/` without modifying imported Phase
  3 code.
- Add configuration schemas and run manifests.
- Test split isolation, content hashing, and token accounting.

### WP2 - Adapt the unchanged baseline to ReguSum and three generators

- Implement dataset adapter only.
- Implement T5, BART, and PEGASUS generation adapters.
- Verify four-group selection and two-stage generation remain unchanged.

### WP3 - Build and audit the semantic index

- Build index from frozen training IDs.
- Cache embeddings and metadata.
- Run retrieval-only smoke tests and manual audit.

### WP4 - Source-query RAG

- Implement group query formation.
- Retrieve, deduplicate, pack, and cache evidence.
- Run a small paired pilot against Base.

### WP5 - Summary-query RAG

- Cache generated draft group briefs.
- Query with draft briefs and regenerate under the same budget.
- Compare retrieval relevance before full generation.

### WP6 - Citation-guided and hybrid RAG

- Adapt audited citation components from Phase 1.
- Add direct-target and hybrid candidate generation.
- Add shuffled evidence control.

### WP7 - Frozen pilot and power check

- Use a preselected pilot set.
- Estimate variance and the number of eligible documents.
- Freeze the full-run matrix.

### WP8 - Full generation and evaluation

- Run sequential, resumable generation.
- Validate manifests before evaluation.
- Report paired results without changing the configuration post hoc.

## 11. Decisions required before implementation

1. Exact ReguSum train/development/test document IDs.
2. Pre-trained only, fine-tuned only, or both adaptation states.
3. Group-level retrieval versus one retrieval pass per document.
4. Exact embedding checkpoint and vector database used in the published work.
5. Top-K and evidence-budget selection policy.
6. Whether citation-guided RAG is part of the first paper or a later extension.

Until these are resolved, create tests and read-only audits only. Do not start a
full generation run.
